# 硬件构建与性能研究

## 当前实现

掌检测 ONNX 第 3、7、11、21、25、29 号节点使用 FP32 深度卷积 PL 核；其余算子在 CPU。核为 100 MHz、25 个卷积位置并行、输入片上缓存。关键点网络用 CPU ncnn FP32，NEON/裁剪优化不应描述为关键点 PL 加速。手部网络前缀 HLS 实验仍为未启用版本。

## 构建顺序

先 `build hls` 查看命令，环境满足后加 `--execute`，完成 C 仿真、综合、RTL 协仿真和 IP 导出；随后 `build overlay --execute` 实现联合硬件。两步使用同一 `EYE_BUILD_DIR`，既有工程目录拒绝覆盖。当前历史工具为 2024.1，指南推荐版兼容性未重验。

`build ncnn --execute` 在 ARMv7 Cortex-A9 Linux 环境构建 ncnn 和桥接库，需要 CMake/g++/OpenMP。源码 ZIP 与许可证随工程保存，模型转换保持原 FP32 权重。不能直接在 Windows x64 编译得到板端可用库。

## 验证顺序

1. 同输入比较 CPU 黄金参考与 PL 的层输出、整网输出和后处理特征；覆盖零输入、随机输入、真实图像、非法尺寸及边界。
2. 核对 LUT/BRAM/DSP、时钟、DRC、WNS/WHS，避免只检查 HLS 延迟估计。既有实现 LUT 18,332、BRAM tile 35、DSP 138，WNS +0.385 ns、WHS +0.026 ns。
3. 部署前确认 bit/hwh 和 owner/RPC 版本；运行中监测租约、generation、DMA idle 与 CPU 回退。
4. 同批输入分别报告网络、IPC、裁剪、采集、状态机等待和主机动作响应。warm/cold、线程数与并发负载分别注明。

旧基准：掌检测 854.4→757.1 ms，含 IPC 约 777.1 ms；完整 TRACK 781→466.7 ms。实时采集并发时曾有 1–2 秒跟踪耗时，因此不能承诺 0.46 秒是现场响应上限。

原基准脚本通过 `locate` 定位：`tools/palm_pl_20261028/benchmark_pl.py`、`benchmark_rpc.py`，`tools/gesture_latency_20261028/verify_pipeline.py`、`check_pose_integration.py`。需要恢复原布局并检查板端路径；先选离线输入避免无意发送 HID。生产报告在 `build/reports/`，新结果独立命名，不覆盖黄金参考。

## 测量输入、分支与完成标准

输入固定为同批图像或同一段回放，并记录权重/源码摘要、后端、线程数、预热次数、测量次数、摄像机并发状态。原始样本至少记录 frame_id、DETECT/TRACK、warm/cold、阶段、耗时和失败原因。设备内部耗时用单调时钟；跨板卡和主机测量先说明时钟对齐方法，不能直接相减未同步时间戳。

| 观测 | 优先排查 |
|---|---|
| 掌检测调用慢 | 六层选择、PL 传输、RPC、其余 CPU 层 |
| TRACK 慢而掌检测很少运行 | 关键点后端是否实际加载、裁剪、线程及采集争用 |
| 模型耗时低但页面动作晚 | 新帧队列、结果年龄、姿态确认时间、HID 去重及主机焦点 |
| 预览 FPS 高而识别慢 | 分别测采集和推理，不以显示帧率代替推理吞吐 |
| cold 与 warm 差距大 | 模型初始化、动态库加载、缓存；分组统计 |

同组样本分别统计数量、失败数、中位数、P95 和最大值；样本过少时标明分位数不稳定。全量 PL 替换是否有收益必须实测，不能由单层加速推断。吞吐可能并发重叠，不直接把分项中位数相加当作端到端中位数。

完成标准：正确性回归保持、原始样本可复核、条件一致、报告后端及分项/端到端口径；硬件与现场条件缺失时只交付测量方案和已有证据。原始记录可采用 [实验记录模板](../assets/experiment_record.md)。
